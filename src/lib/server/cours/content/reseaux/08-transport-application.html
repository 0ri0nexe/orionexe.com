Chapitre 08

Couches transport et application, DHCPv4

IP sait amener un paquet jusqu'à la bonne machine, mais pas jusqu'au bon programme, et il ne garantit rien. La couche transport (TCP ou UDP) livre les données à la bonne application, avec ou sans fiabilité. Au-dessus, les protocoles applicatifs (HTTP, DNS, mail, FTP, DHCP) définissent ce que les programmes se disent.

L'essentiel en 30 secondes
  • La couche transport identifie l'application par un numéro de port (16 bits). Adresse IP + port = socket.
  • TCP : orienté connexion, fiable, ordonné, contrôle de flux. Ouverture en 3 temps (SYN, SYN-ACK, ACK), fermeture en 4 temps (FIN, ACK, FIN, ACK). En-tête de 20 octets.
  • UDP : sans connexion, sans accusé de réception, sans réordonnancement. En-tête de 8 octets. Pour la voix/vidéo en direct, DNS, DHCP, TFTP, SNMP.
  • Ports à connaître : 20/21 FTP, 22 SSH, 23 Telnet, 25 SMTP, 53 DNS, 67/68 DHCP, 69 TFTP, 80 HTTP, 110 POP3, 143 IMAP, 161 SNMP, 443 HTTPS.
  • DHCPv4 attribue une adresse pour une durée limitée (bail) en 4 messages : Discover, Offer, Request, Ack (DORA). Un routeur relaie le broadcast vers un serveur distant avec ip helper-address.

Le rôle de la couche transport

La couche transport assure la communication logique entre applications qui tournent sur des hôtes différents. C'est le lien entre la couche application et les couches inférieures qui, elles, s'occupent de faire voyager les paquets. Ses responsabilités :

  • Suivre chaque conversation : un même PC peut avoir un navigateur, un client mail et un appel vidéo actifs en même temps.
  • Segmenter les données de l'application en morceaux adaptés au réseau, et les réassembler à l'arrivée.
  • Ajouter un en-tête (ports, numéros de séquence...).
  • Identifier l'application destinataire grâce au numéro de port.

Comme les segments de plusieurs conversations sont entrelacés sur le même lien (multiplexage), aucune application ne monopolise le réseau. IP, lui, ne précise pas comment les données sont transportées : c'est le choix du protocole de transport (TCP ou UDP) qui décide du niveau de fiabilité.

Pour comprendre : l'immeuble et les boîtes aux lettres

L'adresse IP est l'adresse de l'immeuble (la machine). Le port est le numéro de la boîte aux lettres (l'application). Le facteur IP dépose le courrier au bon immeuble ; la couche transport le met dans la bonne boîte. TCP ajoute en plus le recommandé avec accusé de réception ; UDP, c'est la carte postale.

Le choix dépend de l'application :

  • TCP quand toutes les données doivent arriver, dans l'ordre : une page web, un fichier, un mail. Un octet manquant rendrait le résultat inutilisable.
  • UDP dans trois cas : le temps réel (voix, vidéo en direct), qui tolère quelques pertes mais pas le retard ; les requête/réponse courtes (DNS, DHCP), où il est plus rapide de reposer la question que d'ouvrir une connexion ; les applications qui gèrent elles-mêmes la fiabilité (TFTP, SNMP).
Piège classique : « UDP est moins bien que TCP »

UDP n'est pas un TCP raté. Pour un appel vidéo, retransmettre une image arrivée trop tard ne sert à rien : elle est déjà périmée, et l'attendre bloquerait les suivantes. L'absence de connexion et de retransmission est exactement ce qu'on veut.

Numéros de port et sockets

Chaque segment porte un port source (l'application qui envoie, sur l'hôte local) et un port destination (l'application visée sur l'hôte distant). L'association adresse IP + port s'appelle un socket, noté par exemple 192.168.1.7:49200. Une connexion est identifiée par la paire de sockets client et serveur.

Pour comprendre : deux onglets vers le même site

Vous ouvrez deux onglets sur www.cisco.com. Les deux connexions vont vers le même socket serveur (IP-serveur:80). Le système du client leur attribue deux ports source différents, par exemple 49152 et 49153 : les deux paires de sockets sont distinctes, donc les réponses reviennent dans le bon onglet.

Piège classique : quel port est « bien connu » ?

Le port bien connu est celui du serveur, en destination de la requête. Le client, lui, utilise un port éphémère en source. Dans la réponse, les deux s'inversent : source 80, destination 49152.

Côté serveur, une application qui écoute sur un port rend ce port ouvert : la couche transport accepte les segments qui lui sont adressés. Deux services ne peuvent pas utiliser le même port avec le même protocole de transport sur un serveur. Pour voir les connexions d'une machine, on utilise netstat (une connexion inexpliquée peut être un signe de compromission) :

C:\> netstat
Proto  Local Address          Foreign Address          State
TCP    192.168.1.124:3158     207.138.126.152:http     ESTABLISHED
TCP    192.168.1.124:3166     www.cisco.com:http       ESTABLISHED

À gauche, le socket local avec un port éphémère ; à droite, le socket distant sur le port 80 (affiché http).

Ouverture et fermeture d'une connexion TCP

Le three-way handshake

  1. Le client demande une session client vers serveur : SYN.
  2. Le serveur acquitte cette session et demande la session serveur vers client : SYN-ACK.
  3. Le client acquitte la session serveur vers client : ACK.

Cet échange vérifie que le destinataire est présent sur le réseau, qu'un service écoute sur le port visé, et le prévient que le client veut ouvrir une session sur ce port. C'est aussi pendant le handshake que les hôtes négocient des options comme le MSS et le SACK.

Pour comprendre : pourquoi 3 et pas 2 ?

Une connexion TCP, ce sont deux flux, un dans chaque sens, et chacun a son propre numéro de séquence à faire acquitter. Il faudrait donc 4 messages (SYN, ACK, SYN, ACK), mais le serveur fusionne son ACK et son SYN dans le même segment. D'où 3.

La fermeture en 4 temps

  1. Le client n'a plus rien à envoyer : FIN.
  2. Le serveur acquitte : ACK. Le sens client vers serveur est fermé.
  3. Quand il a fini à son tour, le serveur envoie son FIN.
  4. Le client acquitte : ACK. La connexion est terminée.

Ici, ACK et FIN du serveur ne sont pas fusionnés, parce que le serveur peut avoir encore des données à envoyer entre les étapes 2 et 3.

Fiabilité et contrôle de flux

Numéros de séquence et retransmission

Les segments peuvent emprunter des routes différentes, arriver dans le désordre ou se perdre. TCP numérote les octets envoyés (numéro de séquence). Le récepteur remet les segments dans l'ordre et renvoie un ACK qui indique le prochain octet attendu. Tout ce qui n'est pas acquitté au bout d'un certain temps est retransmis.

Avec le SACK (Selective Acknowledgment, négocié au handshake), le récepteur peut préciser quels blocs non contigus il a reçus. L'émetteur ne renvoie alors que les morceaux manquants, au lieu de tout ce qui suit le trou.

Pour comprendre : un exemple chiffré

L'émetteur envoie 4 segments de 1000 octets (octets 1 à 4000). Le segment 2 (octets 1001 à 2000) se perd. Sans SACK, le récepteur ne peut que répéter « ACK 1001 » (j'attends l'octet 1001), et l'émetteur risque de renvoyer les segments 2, 3 et 4. Avec SACK, il dit « ACK 1001, mais j'ai déjà 2001 à 4000 » : seul le segment 2 est renvoyé.

Fenêtre et taille maximale de segment

Le contrôle de flux évite de noyer un récepteur qui manque de mémoire ou de puissance. Le récepteur annonce dans chaque segment une taille de fenêtre : le nombre d'octets que l'émetteur peut envoyer sans attendre d'acquittement. S'il est débordé, il réduit la fenêtre ; s'il suit, il l'agrandit.

Le MSS (Maximum Segment Size) est la quantité maximale de données qu'un segment peut porter. Il se déduit de la MTU Ethernet :

MTU Ethernet           1500 octets
− en-tête IPv4           20
− en-tête TCP            20
= MSS                  1460 octets
Piège classique : contrôle de flux et contrôle de congestion

Le contrôle de flux protège le récepteur (sa fenêtre). Le contrôle de congestion protège le réseau : quand un routeur saturé jette des paquets, les pertes servent de signal et TCP ralentit grâce à des timers et des algorithmes dédiés. Deux problèmes différents, tous deux gérés par TCP.

Fonctionnement d'UDP

UDP n'établit pas de connexion et n'envoie aucun trafic de gestion : c'est ce qui le rend léger. Il ne suit pas de numéros de séquence, donc il ne peut pas réordonner : il passe les données à l'application dans l'ordre d'arrivée. Le serveur UDP écoute sur un port bien connu ou enregistré ; le client choisit un port source dynamique et garde la même paire de ports pour tous les datagrammes de l'échange.

La couche application

Dans le modèle TCP/IP, la couche application regroupe les trois couches hautes de l'OSI (application, présentation, session). Elle fait l'interface entre les programmes et le réseau. Ses protocoles définissent le format des messages et les règles de dialogue ; source et destination doivent utiliser un protocole compatible.

Le web : HTTP et HTTPS

Pour afficher http://www.cisco.com/index.html, le navigateur :

  1. Découpe l'URL : le protocole (http), le nom du serveur (www.cisco.com), le fichier demandé (index.html).
  2. Demande à un serveur DNS l'adresse IP de www.cisco.com, s'y connecte (TCP 80), puis envoie une requête GET pour index.html.
  3. Le serveur renvoie le code HTML de la page.
  4. Le navigateur interprète le HTML et affiche la page.

HTTP est un protocole requête/réponse. Trois méthodes courantes : GET (demander des données, une page), POST (envoyer des données, un formulaire), PUT (déposer une ressource, une image). HTTP n'est pas chiffré : on utilise HTTPS (TCP 443) pour tout échange sensible.

Le courrier : SMTP, POP3, IMAP

Le mail fonctionne en stockage et retransmission (store and forward) : les messages attendent sur des serveurs. On utilise un protocole pour envoyer et un autre pour relever.

Piège classique : qui sert à recevoir ?

SMTP n'est jamais utilisé pour relever sa boîte : il sert uniquement à envoyer. Pour recevoir, c'est POP3 ou IMAP.

La résolution de noms : DNS

Le DNS traduit un nom de domaine complet (FQDN, comme www.cisco.com) en adresse IP (comme 198.133.219.25), beaucoup moins facile à retenir. Il utilise le port 53, en UDP pour les requêtes courantes et en TCP pour les réponses volumineuses.

EnregistrementContenu
AAdresse IPv4 d'un hôte
AAAAAdresse IPv6 d'un hôte (« quad-A »)
NSServeur de noms faisant autorité pour la zone
MXServeur de messagerie du domaine

Un serveur DNS cherche d'abord dans ses propres enregistrements. S'il ne sait pas, il interroge d'autres serveurs, puis met en cache la réponse pour les prochaines requêtes. Tous les messages DNS ont le même format en quatre sections : question, réponse, autorité (vers les serveurs qui font autorité), informations additionnelles.

Le DNS est hiérarchique : la racine, puis les domaines de premier niveau (.com pour les entreprises, .org pour les associations, .au pour l'Australie...), puis les domaines en dessous. Chaque serveur ne gère que sa zone et transmet les autres requêtes au serveur compétent. L'outil nslookup interroge manuellement le DNS configuré sur la machine, pour vérifier ou dépanner la résolution.

C:\> nslookup www.cisco.com
Server:   dns.local      ! le serveur DNS configuré par défaut
Name:     www.cisco.com
Address:  198.133.219.25

Le partage de fichiers : FTP et SMB

FTP utilise deux connexions TCP : une connexion de contrôle sur le port 21 (commandes du client, réponses du serveur), ouverte pendant toute la session, et une connexion de données sur le port 20, créée à chaque transfert. Le transfert va dans les deux sens : téléchargement (pull) ou envoi (push).

SMB (Server Message Block) est un protocole requête/réponse de partage de fichiers et d'imprimantes. Ses messages servent à ouvrir, authentifier et fermer des sessions, contrôler l'accès aux fichiers et imprimantes, et échanger des messages entre applications. Contrairement à FTP, le client garde une connexion longue et accède aux ressources distantes comme si elles étaient locales (un lecteur réseau sous Windows).

DHCPv4

DHCPv4 attribue automatiquement l'adresse IPv4, le masque, la passerelle par défaut, le serveur DNS et d'autres paramètres. C'est l'adressage dynamique, par opposition à l'adressage statique saisi à la main. En pratique on mélange les deux : DHCP pour les postes utilisateurs, statique pour les équipements que d'autres doivent retrouver (routeurs, switchs, serveurs, imprimantes).

Le serveur prend une adresse dans une plage configurée, le pool, et la prête au client pour une durée limitée : le bail (lease), typiquement de 24 heures à une semaine. Le client doit recontacter le serveur pour le prolonger. Un client éteint ou parti ne renouvelle pas : à l'expiration, l'adresse revient dans le pool.

Obtenir un bail : DORA

  1. Discover : au démarrage, le client n'a pas d'adresse et ne connaît aucun serveur. Il envoie un broadcast pour trouver les serveurs DHCP.
  2. Offer : un serveur propose un bail (adresse, masque, passerelle, DNS, durée). Plusieurs serveurs peuvent répondre ; le client en choisit un.
  3. Request : le client indique quel serveur et quelle offre il accepte.
  4. Ack : le serveur confirme, le bail est actif. Si l'offre n'est plus valable, il répond Nak et le client recommence.
Pour comprendre : pourquoi le Request est-il encore en broadcast ?

Si deux serveurs ont fait une offre, le Request en broadcast prévient les deux en même temps : le serveur choisi confirme, l'autre comprend que son offre est refusée et remet l'adresse proposée dans son pool.

Renouvellement : avant l'expiration, le client envoie directement (unicast) un DHCPREQUEST au serveur qui lui a donné le bail, qui répond DHCPACK. Deux messages suffisent. Sans réponse à temps, le client passe en broadcast pour qu'un autre serveur prolonge le bail.

Dans le message DHCP, les champs importants sont : l'adresse IP attribuée au client, l'adresse du serveur DHCP, l'adresse de l'agent relais (champ giaddr : le premier routeur qui a relayé la requête), et l'adresse MAC du client, pour la traçabilité.

Piège classique : DHCPv6 et la passerelle

DHCPv6 (messages SOLICIT, ADVERTISE, INFORMATION REQUEST, REPLY) ne fournit pas la passerelle par défaut. En IPv6, elle s'obtient uniquement par le Router Advertisement du routeur.

Configurer un serveur DHCPv4 sur un routeur Cisco

En entreprise, le DHCP tourne en général sur un serveur dédié et le routeur fait seulement relais. Dans une petite agence, le routeur peut lui-même être serveur. Trois étapes :

R1(config)# ip dhcp excluded-address 192.168.10.1 192.168.10.9   ! 1. réserver les adresses statiques
R1(config)# ip dhcp pool LAN-POOL-1                             ! 2. créer le pool
R1(dhcp-config)# network 192.168.10.0 255.255.255.0          ! 3. plage d'adresses
R1(dhcp-config)# default-router 192.168.10.1                  ! passerelle
R1(dhcp-config)# dns-server 192.168.11.5
R1(dhcp-config)# domain-name example.com
R1(dhcp-config)# lease 7                                       ! bail de 7 jours

network et default-router sont indispensables ; les autres sont optionnels (netbios-name-server existe aussi). Vérification : show ip dhcp binding liste les associations adresse IP / adresse MAC distribuées. Côté PC, ipconfig /all montre l'adresse, le masque, la passerelle, le DNS et le suffixe reçus.

Piège classique : oublier l'exclusion

Sans ip dhcp excluded-address, le routeur peut distribuer sa propre adresse (192.168.10.1) ou celle d'un serveur à un PC : conflit d'adresses garanti. Les adresses exclues sont celles déjà attribuées à la main.

Le relais DHCP

Le Discover est un broadcast, et un routeur ne transmet pas les broadcasts. Si le serveur DHCP est sur un autre réseau, le PC ne le trouve jamais. On configure donc le routeur en agent relais, sur l'interface côté clients :

R1(config)# interface g0/0/0                     ! interface qui reçoit le broadcast des PC
R1(config-if)# ip helper-address 192.168.11.6   ! adresse du serveur DHCP
R1# show ip interface g0/0/0                   ! vérifier « Helper address is 192.168.11.6 »

R1 reçoit le broadcast et le renvoie en unicast au serveur, en indiquant sa propre adresse d'interface dans giaddr. Le serveur sait ainsi de quel sous-réseau vient la demande et choisit le bon pool.

Par défaut, ip helper-address relaie huit services UDP : Time (37), TACACS (49), DNS (53), DHCP/BOOTP serveur (67) et client (68), TFTP (69), NetBIOS nom (137) et datagramme (138).

Testez-vous

1. Une même machine fait tourner un serveur web et un serveur SSH. Comment la couche transport sait-elle à qui remettre un segment ?

Grâce au port destination : 80 (ou 443) pour le web, 22 pour SSH. L'IP amène le paquet à la machine, le port l'amène à l'application.

2. Citez trois mécanismes qui rendent TCP fiable et qu'UDP n'a pas.

Les numéros de séquence (réordonnancement), les acquittements avec retransmission des données perdues, la fenêtre (contrôle de flux). On peut ajouter l'établissement de session.

3. Pourquoi la VoIP utilise-t-elle UDP plutôt que TCP ?

Elle tolère quelques pertes mais pas le retard. Retransmettre un morceau de voix arrivé trop tard est inutile et bloquerait la suite. L'en-tête d'UDP est aussi plus léger (8 octets contre 20).

4. Quels flags voit-on dans les trois segments du handshake, puis dans une fermeture normale ?

Ouverture : SYN, SYN + ACK, ACK. Fermeture : FIN, ACK, FIN, ACK.

5. Un PC ouvre une page web. Donnez des ports source et destination plausibles pour la requête, puis pour la réponse.

Requête : source 49152 (éphémère, choisi par l'OS), destination 80. Réponse : source 80, destination 49152.

6. Avec une MTU Ethernet de 1500 octets, quel est le MSS en IPv4 et d'où vient-il ?

1460 octets = 1500 moins 20 (en-tête IPv4) moins 20 (en-tête TCP).

7. Un utilisateur lit ses mails sur son téléphone et son PC, et veut les retrouver sur les deux. POP3 ou IMAP ?

IMAP : les messages restent sur le serveur et les actions sont synchronisées. POP3 les télécharge et les supprime du serveur.

8. Quel enregistrement DNS donne le serveur mail d'un domaine ? Et l'adresse IPv6 d'un hôte ?

MX pour le serveur mail, AAAA pour l'adresse IPv6 (A pour IPv4, NS pour le serveur de noms).

9. Pourquoi FTP utilise-t-il deux ports ?

Le port 21 porte la connexion de contrôle (commandes), ouverte toute la session ; le port 20 porte une connexion de données, ouverte à chaque transfert.

10. Donnez les quatre messages DHCP dans l'ordre, et ceux qui suffisent pour renouveler un bail.

Discover, Offer, Request, Ack (DORA). Pour renouveler : Request (en unicast vers le serveur d'origine) puis Ack.

11. Les PC du réseau 192.168.10.0/24 n'obtiennent pas d'adresse, le serveur DHCP est en 192.168.11.6. Que manque-t-il, et où ?

Le routeur ne relaie pas les broadcasts. Il faut ip helper-address 192.168.11.6 sur l'interface du routeur côté PC (celle qui reçoit le Discover).

12. À quoi sert ip dhcp excluded-address ?

À empêcher le serveur de distribuer des adresses déjà attribuées statiquement (passerelle, serveurs, imprimantes), ce qui créerait des conflits d'adresses.
