TP : analyse de traces GSM

Lire une capture de l'interface radio GSM octet par octet : qui est appelé, sur quel canal, avec quel chiffrement, et ce que contient le SMS.

L'énoncé n'était pas sur Moodle : cette fiche est reconstruite à partir du seul fichier fourni, sms.xml, décodé avec decode_gsm.py.

L'essentiel en 30 secondes
  • La trace contient 175 blocs, tous descendants (BTS vers mobile), d'une cellule MCC 246 / MNC 03 (Lituanie), LAC 4, CI 0x405C.
  • On y voit deux transactions SMS sur SDCCH : un envoi (CM Service Request, type 4 = SMS) puis une réception (paging par IMSI).
  • Le SMS reçu est lisible : « abc », envoyé par +37067659766 via le SMSC +37068499199, horodaté 12/04/2007 20:36:34 (UTC+3).
  • Le réseau active A5/1 avant le SMS, pourtant le contenu est en clair : la trace a été déchiffrée avant l'export.
  • Le SMS fait 37 octets, il est segmenté sur 2 trames LAPDm (bit M) sur le SAPI 3.

La trace et ses champs

Le fichier est un dump XML de l'interface radio Um : chaque élément <l1> est un bloc de 23 octets reçu sur un canal logique, avec un <l2> qui isole la partie utile. L'outil de capture n'est pas nommé (format proche des outils airprobe / OsmocomBB, sans certitude).

Le scénario reconstitué

Hors du bruit du CCCH (paging d'autres abonnés, assignations GPRS), deux transactions passent sur le SDCCH écouté.

  1. FN 268258 à 269260, envoi d'un SMS. Immediate Assignment (RA 0x1D, SDCCH/8 sous-canal 7), puis l'UA renvoie le CM Service Request du mobile (service 4 = SMS, TMSI 2D566F0D). Chiffrement A5/1, nouveau TMSI 2D81E7CD, ouverture du SAPI 3, CP-ACK puis CP-DATA / RP-ACK (référence 1) : le SMS est accepté. Son texte, montant, n'est pas capté.
  2. FN 270192 à 271182, réception d'un SMS, détaillée dans le schéma ci-dessous.
Comment on voit les messages montants

En LAPDm, la BTS répond au SABM du mobile par un UA qui recopie son contenu (résolution de contention) : c'est ainsi qu'on lit le Paging Response et le CM Service Request sans capter le sens montant. Les trames RR N(R) trahissent aussi chaque trame I reçue du mobile.

Décoder un message à la main

Exemple : le SMS reçu, segmenté sur deux blocs SDCCH (FN 270774 et 270825). On retire les 3 octets LAPDm de chaque bloc, on concatène, puis on lit les couches CP, RP et TPDU.

0F 02 45  bloc 2 : N(S)=1, L=17, M=0 (dernier segment)

Deux règles suffisent pour les champs :

  • BCD semi-octets : chaque octet porte deux chiffres, poids faible d'abord, F sert de bourrage. 73 60 se lit 3, 7, 0, 6.
  • GSM 7 bits : les caractères de 7 bits sont tassés, bit de poids faible d'abord. 61 donne 0x61 = « a » ; le bit restant (0) + les 6 bits bas de F1 donnent 0x62 = « b » ; les 2 bits hauts de F1 + les 5 bits bas de 18 donnent 0x63 = « c ».

Les deux transactions ont la même Classmark 2 (33 19 81) et sont séparées de 11,5 s : il est plausible (non prouvé) qu'un même téléphone se soit envoyé « abc » à lui-même.

Pourquoi le SMS est-il lisible ?

Le Ciphering Mode Command (06 35 01 : SC=1, algorithme 000 = A5/1) est émis en clair. Dès que le mobile a répondu (son Ciphering Mode Complete est acquitté par le RR de FN 270570), tout le SDCCH est chiffré sur l'air. Si on lit le TMSI réalloué et le SMS, c'est que la capture a été déchiffrée avec la clé Kc (clé connue, réseau de test ou A5/1 cassé) avant l'export. Une capture brute ne montrerait que des octets aléatoires à partir du TMSI Reallocation Command (FN 270621).

Questions types et outils

Questions qu'un énoncé poserait

1. Quel réseau, quelle cellule ?

Le SI3 (06 1B 40 5C 42 F6 30 00 04) donne CI = 0x405C, MCC 246 (Lituanie), MNC 03, LAC 0x0004. BSIC 22. Les SI1 à SI4 tournent selon TC = (FN / 51) mod 8.

2. Que contient le CCCH ?

83 Paging Request (78 de type 1, dont 33 vides « aucune identité », 3 de type 2, 2 de type 3), 18 Immediate Assignment (dont 5 pour des TBF GPRS) et 9 blocs vides. Les pagings de type 1 visent 56 TMSI et 5 IMSI distincts.

3. Comment le destinataire est-il appelé ? Est-ce un problème ?

Par un Paging Request Type 1 portant son IMSI en clair, et non un TMSI. N'importe quel récepteur passif peut donc relier cet IMSI à l'arrivée d'un SMS. Le réseau corrige ensuite en réallouant un TMSI (chiffré).

4. Quel canal dédié est attribué et pourquoi ?

Immediate Assignment FN 270329 : SDCCH/8 sous-canal 3, TS1, avec saut de fréquence (MAIO 1, HSN 41), TA = 1. La Request Reference RA = 0x9C (100xxxxx) signifie « réponse à un paging ». Les blocs SDCCH ont FN mod 51 = 15, soit la fin des trames 12 à 15 : le sous-canal 3 de la multitrame SDCCH/8, ce qui confirme l'association.

5. Pourquoi le SMS passe-t-il sur le SAPI 3 et en deux trames ?

LAPDm réserve le SAPI 0 à la signalisation RR/MM/CC et le SAPI 3 aux SMS. Un bloc SDCCH de 23 octets laisse au plus 20 octets utiles après l'en-tête de 3 octets : le CP-DATA de 37 octets est coupé en 20 + 17, le bit M signalant la suite.

6. Le SMS envoyé (première transaction) a-t-il abouti ?

Oui : le réseau répond CP-ACK puis CP-DATA contenant un RP-ACK (référence 1), puis libère le canal. Le texte envoyé est montant, il n'est pas dans la trace.

7. Combien de temps dure la réception du SMS ?

Du paging (FN 270192) au dernier UA (FN 271182) : 990 trames × 4,615 ms ≈ 4,6 s. Le SDCCH/8 n'offre qu'un bloc par multitrame de 51 trames (235 ms), d'où la lenteur.

Outils

  • Script : python3 -I decode_gsm.py sms.xml (télécharger) imprime une ligne par bloc, reconstitue les segments LAPDm et décode le SMS. Il ne couvre que les messages de cette trace.
  • Wireshark ne lit pas ce XML. Il faut réémettre chaque bloc en GSMTAP (UDP 4729, avec le type de canal défini dans gsmtap.h) ou produire un pcap ; les dissecteurs gsmtap, lapdm, gsm_a et gsm_sms font alors le travail, filtrables avec gsm_sms.
  • Pour une capture réelle aujourd'hui : gr-gsm ou OsmocomBB produisent directement du GSMTAP vers Wireshark.
